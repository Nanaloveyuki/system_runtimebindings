# Android capability reference

Implementation reference for prospective Android runtime bindings, with detailed asset-read requirements and a small read-only device-information snapshot. Runtime version and selected metadata can precede assets; asset implementation depends on a public AJNI host Context contract. Later candidates below are research boundaries, not implemented capabilities or compatibility claims. Official references checked 2026-11-03. Extend this note when a capability enters scope; recheck its linked API contract and target-SDK behavior before implementation, and replace stale findings rather than accumulating a documentation mirror. See [platform versions](android-platform-versions.md) for the version/test-evidence boundary.

## Packaged asset reads

The bounded asset capability is reading one named file from the consuming application's packaged `assets/` directory into binary bytes, once the AJNI dependency below is satisfied. It does not introduce a general resource framework, filesystem access, URI resolution, or directory enumeration.

| Concern | Official contract and binding implication |
| --- | --- |
| Acquisition | [`Context.getAssets()`](https://developer.android.com/reference/android/content/Context#getAssets()) returns the application's package `AssetManager`; it exists from API 1. [`AssetManager.open(String)`](https://developer.android.com/reference/android/content/res/AssetManager#open(java.lang.String)) also exists from API 1 and returns an `InputStream`. These platform thresholds do not establish this repository's supported/tested Android range. |
| Names and directories | [`open`](https://developer.android.com/reference/android/content/res/AssetManager#open(java.lang.String)) accepts hierarchical names for files under `assets/`. Use an asset-relative name such as `data/config.bin`, not an absolute device path or an `assets/` prefix. [`list(String)`](https://developer.android.com/reference/android/content/res/AssetManager#list(java.lang.String)) documents relative directory paths and names relative to that directory; enumeration can remain outside the first read contract. |
| Access mode | The one-argument [`open`](https://developer.android.com/reference/android/content/res/AssetManager#open(java.lang.String)) uses [`ACCESS_STREAMING`](https://developer.android.com/reference/android/content/res/AssetManager#ACCESS_STREAMING), defined as sequential reads with occasional forward seeks. [`ACCESS_BUFFER`](https://developer.android.com/reference/android/content/res/AssetManager#ACCESS_BUFFER) attempts to load content into memory for fast small reads. Both constants exist from API 1. A sequential whole-file read can use streaming; buffer mode is an access hint, not a promise of a zero-copy MoonBit buffer. |
| Read loop | [`InputStream.read(byte[], int, int)`](https://developer.android.com/reference/java/io/InputStream#read(byte[],%20int,%20int)) exists from API 1, can return fewer bytes than requested, blocks, and reports end-of-stream as `-1`. Preserve only the returned byte count and continue until EOF. [`available()`](https://developer.android.com/reference/java/io/InputStream#available()) is an estimate of nonblocking readable bytes; do not use it as the general whole-file sizing/EOF contract. |
| Errors | [`open`](https://developer.android.com/reference/android/content/res/AssetManager#open(java.lang.String)) declares `IOException`; [`read`](https://developer.android.com/reference/java/io/InputStream#read(byte[],%20int,%20int)) can also fail with I/O errors. A missing asset or failed read must produce an observable failure, not an empty success or partial successful result. The binding must specify its error representation without assuming every Java `IOException` is the same missing-file error. |
| Stream lifetime | [`AssetInputStream.close()`](https://developer.android.com/reference/android/content/res/AssetManager.AssetInputStream#close()) releases its associated system resources; [`InputStream.close()`](https://developer.android.com/reference/java/io/InputStream#close()) declares possible I/O failure. The proposed whole-file operation owns each stream it opens and closes it on success and failure; it returns owned bytes, not a live Java stream. A close failure must not silently turn a failed read into success or erase the original read failure. |

JNI descriptors to carry into the eventual adapter are below, derived from the linked Java signatures. Preparation cross-checked `AssetManager` and `Build.VERSION` against API 36 `android.jar` using `javap -s`; stream API availability was checked in SDK metadata and Android's reference. Host-JDK `javap java.io.InputStream` is not Android availability evidence. These descriptors do not imply an AJNI Context acquisition API exists.

| Java member | JNI descriptor |
| --- | --- |
| [`Context.getAssets()`](https://developer.android.com/reference/android/content/Context#getAssets()) | `()Landroid/content/res/AssetManager;` |
| [`AssetManager.open(String, int)`](https://developer.android.com/reference/android/content/res/AssetManager#open(java.lang.String,%20int)) | `(Ljava/lang/String;I)Ljava/io/InputStream;` |
| [`InputStream.read(byte[], int, int)`](https://developer.android.com/reference/java/io/InputStream#read(byte[],%20int,%20int)) | `([BII)I` |
| [`InputStream.close()`](https://developer.android.com/reference/java/io/InputStream#close()) | `()V` |
| [`android/os/Build$VERSION.SDK_INT`](https://developer.android.com/reference/android/os/Build.VERSION#SDK_INT), static field | `I` |

Calling Java `InputStream.close()` closes the stream resource. AJNI's [`JavaObject::close`](../../.mooncakes/Nanaloveyuki/ajni/src/runtime/runtime.mbt) releases its bridge handle/reference through [`ajni_rt_object_close` / `resource_close`](../../.mooncakes/Nanaloveyuki/ajni/src/runtime/ajni_runtime.c); it does not substitute for invoking the Java stream method. Both cleanups are required for an owned stream handle, with the original read failure preserved if cleanup also fails. Prefer the API 1 `read` loop above to assuming a newer Java convenience method is present across the supported device range.

### Context and threading dependency

AJNI 0.3.6 provides `@android.application_context() -> @runtime.JavaObject raise @runtime.RuntimeError`; see the [accepted AJNI Context contract](ajni-application-context-requirement.md). Asset reads use this host-owned application Context through checked JNI. The binding must close streams it opens, not the host's shared `AssetManager`.

The application-scoped Context is supplied by AJNI's initialized host. `getApplicationContext()` exists from API 1 and avoids retaining an Activity for package resource access. Treat the context-provided manager as borrowed: the binding closes its own streams, not the host's shared manager.

Reads can block under the [`InputStream` contract](https://developer.android.com/reference/java/io/InputStream#read(byte[],%20int,%20int)); callers must keep blocking asset reads off the UI thread, following Android's [threading rules](https://developer.android.com/guide/components/processes-and-threads#Threads). Worker-thread support also depends on AJNI: Android's [JNI guidance](https://developer.android.com/training/articles/perf-jni#javavm-and-jnienv) makes `JNIEnv` thread-local, and its [reference rules](https://developer.android.com/training/articles/perf-jni#local-and-global-references) limit local references to the current native call/thread. Retaining Java objects requires appropriate owned references and release. Do not cache a local context reference or move a `JNIEnv` between threads.

AJNI 0.3.6 currently runs MoonBit on the Android main owner thread; `start_worker()` attaches and posts back to main without executing MoonBit there. Context acquisition alone does not provide off-main resource execution. A small synchronous fixture can verify the JNI path, but general blocking asset reads need a separate host execution/completion contract. Feature shutdown preserves the generic session; existing ordinary JavaObjects must not be assumed invalid merely because the Android feature stopped.

Asset names need correct Java `String` conversion. Android's [JNI string guidance](https://developer.android.com/training/articles/perf-jni#utf-8-and-utf-16-strings) distinguishes UTF-16 and Modified UTF-8 from ordinary UTF-8. A successful ASCII path read does not prove Unicode path handling through AJNI.

### Consumer-visible acceptance for the next read

These are future implementation acceptance criteria, not executed checks:

- A packaged binary fixture returns exactly its original length and bytes, including NUL, bytes above `0x7f`, and data spanning multiple read buffers; no text decoding or signed-byte corruption occurs. An empty packaged file succeeds with empty bytes.
- Nested asset-relative names and packaged Unicode names, including a supplementary Unicode character, return the expected fixture bytes through the public consumer API.
- A missing name fails observably and remains distinguishable from a successful empty asset. A read failure never returns a truncated successful payload.
- Repeated reads of the same name each start at the beginning and return identical bytes. A failed missing-name read does not prevent a later valid read.
- Each operation closes the stream it opened on every exit path; returned bytes remain valid after closing, and later reads still work. Success and failure paths release temporary Java references without closing the host's shared `AssetManager`.
- Calls before host initialization fail through the documented AJNI contract. General blocking reads have an exercised off-main host execution/completion path that keeps MoonBit entry on its owner; a main-thread fixture or native attach/post demo is insufficient evidence.

## Small device-information snapshot

Keep the prospective surface to these static diagnostic fields; no context/service lookup is needed for the listed static fields. Their meanings and introduction levels come directly from their API references:

| Field | Device API availability | Meaning/limit |
| --- | --- | --- |
| [`Build.MANUFACTURER`](https://developer.android.com/reference/android/os/Build#MANUFACTURER) | API 4 | Product/hardware manufacturer. |
| [`Build.MODEL`](https://developer.android.com/reference/android/os/Build#MODEL) | API 1 | End-user-visible product name. |
| [`Build.VERSION.RELEASE`](https://developer.android.com/reference/android/os/Build.VERSION#RELEASE) | API 1 | User-visible opaque string. Do not parse or order it to detect API availability. |
| [`Build.VERSION.SDK_INT`](https://developer.android.com/reference/android/os/Build.VERSION#SDK_INT) | API 4 | Major SDK version of software running on the device; use for relevant device API gates. |

`SDK_INT` is not the app's `targetSdkVersion`: the latter controls compatibility behaviors as documented by [`<uses-sdk>`](https://developer.android.com/guide/topics/manifest/uses-sdk-element#target). Neither a high compile SDK nor a high target SDK makes a newer API exist on an older device. If a future capability needs minor-release API gates, [`SDK_INT_FULL`](https://developer.android.com/reference/android/os/Build.VERSION#SDK_INT_FULL) was added in API 36; keep it outside this minimal snapshot until needed.

Expose these `static final` fields read-only. Android's [targeted behavior changes](https://developer.android.com/about/versions/17/behavior-changes-17#static-final-fields) state that on Android 17+, apps targeting API 37+ crash if JNI attempts to modify a `static final` field. Reading metadata does not require field writes.

Treat these as descriptive diagnostics, not identity or a guaranteed unique device key. Exclude serial numbers, IMEI, Android ID, advertising identifiers, fingerprints assembled from device fields, and other persistent device identifiers from this surface; Android's [identifier guidance](https://developer.android.com/identity/user-data-ids) explains why identifier access and choice require a separate purpose-specific design. Do not add permission prompts or automatic telemetry to this snapshot.

## Later candidates

These rows record bounded follow-on research; they authorize no implementation or manifest changes.

| Candidate | Verified device APIs / permissions | Ownership and semantic limits |
| --- | --- | --- |
| Short vibration | [`Vibrator.vibrate(VibrationEffect)`](https://developer.android.com/reference/android/os/Vibrator#vibrate(android.os.VibrationEffect)) starts at API 26. [`VibratorManager`](https://developer.android.com/reference/android/os/VibratorManager) and its [`getDefaultVibrator()`](https://developer.android.com/reference/android/os/VibratorManager#getDefaultVibrator()) start at API 31. [`VIBRATE`](https://developer.android.com/reference/android/Manifest.permission#VIBRATE) is a normal manifest permission. | Requires AJNI context/service acquisition. Check [`hasVibrator()`](https://developer.android.com/reference/android/os/Vibrator#hasVibrator()) instead of assuming hardware. The cited `vibrate` method says the app should be foreground; do not promise that issuing a call guarantees a perceptible effect. Bound the first contract to one effect/cancellation rather than synchronized multi-vibrator orchestration. |
| Runtime permission request/result | [`Activity.requestPermissions(String[], int)`](https://developer.android.com/reference/android/app/Activity#requestPermissions(java.lang.String[],%20int)) starts at API 23; dangerous permissions must be declared and are asynchronously granted or denied. The [request guide](https://developer.android.com/training/permissions/requesting) requires checking permission state and handling denial/revocation. Normal manifest permissions are granted at install time under the cited Activity contract. | Requires host Activity/UI lifecycle and result delivery through AJNI, not just an application Context. The Activity can pause/resume or be recreated around a request. Keep UI work on the [UI thread](https://developer.android.com/guide/components/processes-and-threads#Threads), and return denial to the caller without blocking unrelated functionality. Permission groups are not a stable grant contract. |
| Network state snapshot | [`getActiveNetwork()`](https://developer.android.com/reference/android/net/ConnectivityManager#getActiveNetwork()) starts at API 23; [`getNetworkCapabilities(Network)`](https://developer.android.com/reference/android/net/ConnectivityManager#getNetworkCapabilities(android.net.Network)) starts at API 21. Thus a default-network snapshot using both is an API 23+ candidate. [`NET_CAPABILITY_VALIDATED`](https://developer.android.com/reference/android/net/NetworkCapabilities#NET_CAPABILITY_VALIDATED) starts at API 23. These queries require [`ACCESS_NETWORK_STATE`](https://developer.android.com/reference/android/Manifest.permission#ACCESS_NETWORK_STATE). | The default network/capabilities can be absent or change. Report capability state rather than a permanent “online” truth: [`NET_CAPABILITY_INTERNET` describes setup, while validation reflects system probes](https://developer.android.com/develop/connectivity/network-ops/reading-network-state#network-capabilities), and neither guarantees a later request to a particular endpoint. Exclude SSIDs and other location-sensitive transport data. |
| Default-network observation | [`registerDefaultNetworkCallback(NetworkCallback)`](https://developer.android.com/reference/android/net/ConnectivityManager#registerDefaultNetworkCallback(android.net.ConnectivityManager.NetworkCallback)) starts at API 24 and requires `ACCESS_NETWORK_STATE`; its explicit [`Handler` overload](https://developer.android.com/reference/android/net/ConnectivityManager#registerDefaultNetworkCallback(android.net.ConnectivityManager.NetworkCallback,%20android.os.Handler)) starts at API 26. | Requires AJNI callback/reference ownership and dispatch into MoonBit. Default callbacks use an internal handler; keep callback work short, and define subscriber lifetime plus [`unregisterNetworkCallback`](https://developer.android.com/reference/android/net/ConnectivityManager#unregisterNetworkCallback(android.net.ConnectivityManager.NetworkCallback)) cleanup. Do not treat the snapshot's API 23 threshold as the default-callback threshold. |

`ACCESS_NETWORK_STATE` permits network information; [`INTERNET`](https://developer.android.com/reference/android/Manifest.permission#INTERNET) permits opening sockets. Both are normal permissions, but their purposes differ: observing network state does not itself need socket access, and `INTERNET` does not replace `ACCESS_NETWORK_STATE` for the cited queries/callbacks.

Local communication is a separate future capability: Android's [Android 17 targeted behavior changes](https://developer.android.com/about/versions/17/behavior-changes-17#local-network-permission) require apps targeting API 37+ to use a system-mediated picker or request `ACCESS_LOCAL_NETWORK` for LAN communication. The network-state rows above neither implement LAN access nor imply that `INTERNET` alone authorizes it.

Permission behavior must be researched per named permission and per device/target combination, not inferred from the existence of the API 23 request mechanism. For example, [Android 13 / API 33 notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission) adds `POST_NOTIFICATIONS` for non-exempt notifications; target 33+ lets the app choose prompt timing, whereas target 32 or lower has system-controlled timing. [Bluetooth permission guidance](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions#declare-android12-or-higher) changes declarations for apps targeting Android 12 / API 31+ and makes `BLUETOOTH_SCAN`, `BLUETOOTH_ADVERTISE`, and `BLUETOOTH_CONNECT` runtime permissions. These illustrate why a later permission binding needs a capability-specific behavior table; they do not expand the current binding scope.
